# Plugin API compatibility

The host loads a plugin whose `api_version` has the same major version as its own (`cfddesk.registry.API_VERSION`). A minor version adds things; it never removes or changes what an older minor version offered, so a `1.0` plugin loads unchanged on a `1.1` host. The one exception is a safety fix, listed under the version that made it (1.2 made `ws.data` paths stricter).

## 1.4

Host API 1.4 (`API_VERSION`, and `hostVersion` in a workspace's context). The workspace SDK (1.1.0), `magnusim_sdk` (1.2.0) and the plugin UI kit are unchanged. A 1.3 plugin loads unchanged.

**Start actions, `[[start_actions]]`.** A study kind with a workspace may declare one start action: a button that creates a study of that kind (named with the first free "<Kind title> N", no prompt) and opens it in its workspace. The host draws it in the empty project, the header, the New Project dialog and Home (`places`, default all four), at most 3 in each place except the New Project dialog, in plugin load order then manifest order. Fields: `study_kind` and `label` (1-40 characters) are required; `hint` (up to 120), `icon` (one SVG path), `places`, `home_label` (1-40) and `header_label` (1-24, needs `"header"` in `places`) are optional. At most one action per kind and one `header` action per workspace; without `header_label` the workspace title must be 24 characters or fewer. Texts are one line with no control or bidirectional characters, and are never shortened by the check (too long is an error); Home cuts a start button's text with "…" only when the window is too narrow, with the whole text in its tooltip. A bad table fails only that plugin ("manifest [[start_actions]]: …"). `authoring.md` has the whole contract.

**`links_geometry`.** A `[[study_kinds]]` key, `true` or `false` (default `false`); `true` needs the kind to have a `workspace`. It is checked from 1.4 and used from 1.5, which adds the call that links a geometry.

**Unknown names in manifest lists are ignored.** From 1.4 on, a value in a manifest list this host does not know (a `places` name a later host added) is left out, with a warning on the plugin's Settings row, so a plugin written for a later host still loads; the table is an error only when nothing it can use is left. This is the rule for every manifest enum from 1.4 on. Unknown keys are ignored, as before.

**Published.** `GET /api/plugins` rows (`plugins.list`) add `start_actions: [{study_kind, kind_title, workspace, workspace_title, label, home_label, header_label, hint, icon, places}]`, filled only for a plugin that is on (`[]` for one that is off, needs setup, failed or is incompatible); `home_label` and `header_label` are `""` when not set. The project tree's `plugin_study_kinds` and `plugin_studies.list`'s `kinds` add `links_geometry` and `start_action` (the same object, or `null`), and are listed in plugin load order (they were sorted by plugin key).

**The project header.** The header button of a kind shown there (left of Workspaces, in a project; a workspace's own header does not show it) opens a menu of that kind's studies and "New <Kind>"; the Workspaces menu no longer lists that kind, and disappears when no kind is left for it. Both menus open from the keyboard (Down, Enter or Space; Up, Down, Home, End; Escape returns the focus to the button; Tab closes).

**Kit formatters and units (`@magnusim/plugin-ui`, same signatures).** `formatSimTime(null)` and `formatSimTime('')` return "—" (were "0 s"); a value that rounds into the next band is written in that band (99.95 gives "100 s", was "100.0 s"); `formatSci(999999.9)` gives "1.0000e+6" (was "1000000"); `unitIsImperial('min')` and `unitIsImperial('mmH₂O')` are `false` (were `true`).

**Mesh contract.** A `MeshBackend` says what the Mesh panel shows for it. `refinement_types` is its refinement menu, from the records the host stores (`cfddesk.registry.mesher.HOST_REFINEMENT_TYPES`: `surface_custom_sizing`, `inflate_boundary_layer`); the refinements API refuses another type on its meshes (400 "<label> does not apply <type> refinements."). `stage_labels` (`(stage, label)`) and `stage_details` (`(stage, regex, label)`, first match wins) name the progress stages its generator reports; a stage with neither shows "Working". `report` (`(result_key, text, otherwise)`) writes the finished mesh's summary from the fields its result records (`hex_core_applied`, `layers_applied`, `surface_size_m` today): an empty key always shows `text`, a true value `text`, a false one `otherwise`, a number fills `{length}`. A refinement type outside the list, an entry of the wrong shape or a pattern that does not compile refuses the mesher when it registers. The keys a mesher's `settings_schema` has beyond the core's (`fineness`, `add_layers`, `physics_based`, `hex_element_core`, `small_feature_suppression`, `gap_refinement_factor`, `global_gradation_rate`) are saved as given in the mesh's `settings.mesher_settings`, at their schema default until changed, and a mesh keeps its mesher's key while that plugin is off. `fingerprint_payload`, `generate`, `supports_hex_core`, `frozen` and `multi_region` are accepted and not read. The built-in meshers now list what they apply: all three take surface custom sizing and inflate layers (the registry used to list volume, extrusion, region and feature refinements that no mesher implements). A mesher plugin still has no run path of its own (ROADMAP).

**Optional analysis fields.** An `AnalysisType` needs only `key`, `label`, `category`, `time_dependency` and `fields`; every other field defaults to empty (`validate` to one that reports nothing), in the 1.0 order, so a 1.0 analysis built by position constructs unchanged. `turbulence_models`, `default_turbulence`, `validate` and `parse_log_line` are accepted as before: the core reads only `default_turbulence`, to seed a new study's `turbulence_model` and `turbulence_model_key` when the study record has none, and calls `validate` only through `run_analysis_validate`. A new study's record is the analysis's `study_defaults`, else its identity (`analysis_type`, `analysis`, `analysis_title`, `category`, `time_dependency`, `algorithm`; it no longer has `flow_group` or empty turbulence keys), and a key the record leaves out is filled from `default_turbulence`, then from the `settings_schema` defaults (before, an analysis with a `study_defaults` hook got neither). Registry rows publish `default_turbulence` and `turbulence_models` only when the analysis sets them.

**Kinematic fields.** `AnalysisType.kinematic_fields` (default `None`, not declared; `()` for none) names the fields its cases store divided by density, which every results view shows times `rho`. Each is a field name (a letter, then up to 63 letters, digits, `_` or `.`, with no `__`); a bad one is a `ContractError`. After `write_case` the core adds the list to the case's `w27-case.json` when the case does not have one (a list the writer put there wins); an analysis that does not declare it leaves the sidecar as its writer wrote it, and a case with no list is still read as `["p"]`. The analysis contract is now `1.4` (`contract` in registry rows); rows add `kinematic_fields` (a list, or `null`), and a `LaunchSpec` adds `kinematic_fields` (`None` by default; the default launch spec takes the analysis's), checked like the analysis's.

## 1.3

Host API 1.3 (`API_VERSION`, and `hostVersion` in a workspace's context), plugin UI kit 1.0.0 (`PLUGIN_UI_API_VERSION`); workspace SDK 1.1.0 and `magnusim_sdk` 1.2.0 are unchanged. A 1.2 plugin loads unchanged.

**The plugin UI kit, `@magnusim/plugin-ui`.** Components and helpers that look like the app's own panels, on the design tokens. In the page a plugin gets the page's own copy as `pluginUi.kit`, and a `.tsx`, `.ts` or `.jsx` UI the host bundles may `import { Button } from '@magnusim/plugin-ui'` (the host resolves it to the same copy). In a workspace frame the import map maps `@magnusim/plugin-ui` to `/plugin-sdk/plugin-ui.js`, and every workspace page links `/plugin-sdk/plugin-ui.css` after `theme.css`. A frame that imports the kit does not start on a 1.2 host: the module does not resolve. Types: `docs/plugins/plugin-ui.d.ts`, also served as `/plugin-sdk/plugin-ui.d.ts`; `docs/plugins/plugin-sdk.json` adds `plugin_ui_version`.

**`pluginUi` adds** `kit`; `panelDone()`, which closes the panel as a core panel's Done does (`cfd:panel-done`); `toast(message, { kind })`, an app toast (`info`, `success` or `error`; any other kind is `info`; 300 characters at most; up to three stack at the bottom right, and none closes while the pointer is on any of them); and `unitSystem()`, `metric` or `imperial` as the open project shows. `registerFieldWidget` is typed `ComponentType<FieldWidgetProps>` (it was `Record<string, unknown>` props).

**Bundled UIs.** The in-page `react` shim exports every name React exports (it had 16, so a UI that imported `useTransition` did not bundle). A bundled UI may import `react`, `react/jsx-runtime`, `@magnusim/plugin-ui` and its own files.

**Field widgets.** A widget registered after a schema form opened now replaces the core control at once (before, the form kept the core control until its schema or data changed).

**Workspace toasts.** `ws.ui.toast` is now drawn as the kit Toast, still inside the workspace (`#workspace-overlay [data-ws-toast]`) and one at a time. Its classes are `mgk-toast mgk-toast--<kind>` (they were `ws-toast is-<kind>`). It closes after 3.8 s, errors after 9 s (both were 4 s), and its time stops while the pointer or the focus is on it.

**Primary colour.** `--mg-primary` stays `#1570ef` (hover `#175cd3`); the app's own primary buttons now use it too.

**Colour.** `useViewer().createRainbowLut()` uses hue 0.667 (was 0.666), the hue the app's own renders use (the kit's `RAINBOW_HUE`).

**Plugin OpenFOAM cases (`ws.compute`).** A workspace writes an OpenFOAM case in its study's folder (`ws.files`, or its own Python through `PluginData`) and the host runs it with OpenFOAM in WSL, on the app's one compute slot (below). Check `context.hostVersion` (1.3 or later); a 1.2 host answers `not_allowed`.

| Call | What it does |
|---|---|
| `compute.submitOpenFOAM({caseRel, app, nProcs?, pre?, results})` | Queues the case in `studies/<sid>/<caseRel>` and resolves `{id, ahead, existing}`. `existing` is true, with that case's id, when the same folder (by its name on disk) is already queued or running |
| `compute.events(id, fn)` | Follows a case of this study: first where it is now (`queued`, `start`, or `end`), then every event; returns a function that stops listening |
| `compute.stop(id, {force?})` | A queued case leaves the queue (`stopped`, "Removed from the queue before it started"); a running one stops by stage (below). Resolves `{status, stopping}` |
| `compute.status(id)`, `compute.list()` | A case, or this study's cases newest first (50 at most), as `{id, caseRel, app, nProcs, status, stage, stopping, ahead, createdAt, startedAt, finishedAt, error, code, result, seq}`; `status` is `queued`, `running`, `done`, `failed`, `stopped` or `lost`, and `result` is `{savedTimes, lastSaved, phases, writeFormat}`. A reopened page finds its running case in the list |

A case runs once: it starts from its `0/` folder, and a folder that already ran (a hidden `.magnusim-ran`, a time folder other than `0`, or a `processor*` folder) is refused with `has_results` ("This case already ran. Write a new case folder for each run."). `caseRel` is 1 to 8 parts joined by `/`, each a letter, digit or `_` then up to 63 letters, digits, `_`, `.` or `-`, not ending in `.`; it must be a folder inside the study, with no link or junction inside it. A name like `__APP__` anywhere in the case's path (the projects folder, the project, the plugin key included) is refused with `invalid_path`, and so is a path with `$`, a backtick, `"` or a control character, and a WSL case folder setting (`MAGNUSIM_WSL_CASE_ROOT`) that holds `'`. `system/controlDict` must name `app` as its `application`; `app` is a plain program name of a registered solver (today `simpleFoam` and `pimpleFoam`; `icoFoam` is refused with `app_not_allowed`). For a solver whose Stop saves the latest time, `controlDict` needs a `stopAt` line and `runTimeModifiable true`; `writeCompression` must be off. Without `constant/polyMesh` a step must make the mesh (`blockMesh` or `gmshToFoam`). `results` says what comes back and how it reads: `kinematicFields` (required, may be empty: the fields stored divided by density, shown times `rho`), `rho` (above 0, required when `kinematicFields` lists a field) and `frameFields` (the fields that mark a saved frame, 8 at most, each a file in `0/`; default `U` and `p` when both are there). Field names are a letter then up to 63 letters, digits, `_` or `.`, with no `__`. `writeFormat` binary and ascii are both read.

`pre` runs up to 16 WSL steps before the solver, in order, each `{tool, args?, parallel?}` with at most 4 arguments of 120 characters. This one table is the whole list; anything else is refused with `pre_not_allowed` (for example "Step 2 (createPatch): -dict is not allowed"), and so are `-case`, `-lib`, `-libs`, `-parallel`, `-roots`, `-fileHandler`, `-region`, `-dict` and `-np`:

| Tool | Arguments | The host adds | Needs in the case | `parallel` |
|---|---|---|---|---|
| `blockMesh` | none | | `system/blockMeshDict` | no |
| `gmshToFoam` | one path to a `.msh` file in the case; `-keepOrientation` may come first | | that file | no |
| `surfaceFeatureExtract` | none | | `system/surfaceFeatureExtractDict` | no |
| `snappyHexMesh` | none or `-overwrite` | `-overwrite` | `system/snappyHexMeshDict` | yes |
| `extrudeMesh` | none | | `system/extrudeMeshDict` | no |
| `changeDictionary` | none | | `system/changeDictionaryDict` | yes |
| `createPatch` | none or `-overwrite` | `-overwrite` | `system/createPatchDict` | yes |
| `checkMesh` | `-allGeometry`, `-allTopology` (each once) | | | yes |
| `renumberMesh` | none or `-overwrite` | `-overwrite` | | yes |
| `decomposePar` | none or `-force` | `-force` | | no |
| `reconstructParMesh` | none or `-constant` | `-constant` | | no |

A `decomposePar` step opens a parallel span and the next `reconstructParMesh` closes it; spans do not nest, every step inside one has `parallel: true`, and a parallel step outside one is refused. A parallel step runs as `mpirun --oversubscribe -np N <tool> <args> -parallel`, the way a parallel solve runs. `nProcs` (1 to 64) is clamped to the PC (its cores, and the MPI slots WSL has); a solver that does not run in parallel and a plan with no parallel step get 1. When the run gets more than one rank the host writes `system/decomposeParDict` (scotch), replacing the case's own. When it gets one, a span runs serially: `decomposePar` and `reconstructParMesh` are skipped (their `pre` event says `skipped: true`) and the steps inside run without `mpirun`, so one plan works on any PC. Each step's output goes to `log.<tool>.<i>` in the case (`i` counts from 1). A step that exits with an error ends the run ("blockMesh failed (exit 1). See log.blockMesh.1 in the case folder"); OpenFOAM v2606's `checkMesh` exits 0 even when a mesh check fails, so it reports in its log and never ends a run. A step that writes a time folder ends it too ("<tool> wrote a time folder").

Events, each with its `seq`: `queued {ahead}`; `start`; `stage {stage}` (`pre_copy_in`, `pre_copy_back`, `copy_to_wsl`, `decompose`, `solve`, `reconstruct`, `copy`, `cleanup`, and the host's `stopping` and `ending`); `ranks {n_procs}`; `pre {tool, index, exit_code, parallel?, n_procs?, skipped?}`; `phase {phase, seconds}` (`pre`, `copy_in`, `decompose`, `solve`, `reconstruct`, `copy_back`); `progress {time, n_steps, residuals, co_max?, co_mean?, delta_t?, points}`, at most four a second, `residuals` the largest initial residual of each field in the last step and `points` the steps since the last one (400 at most); `time_saved {t}`; `warning {code, message}`; `end {status, error, code, result}`. No event carries a path. The status comes from what the case's own runner saw, never from an exit code: `done` only when the run ended cleanly and its frames came back.

Stop works by stage: before the solver, the WSL steps end at once; while the solver runs, it is asked to write its latest time and stop (`stopAt writeNow`), and it is ended after 20 s if it has not; a second Stop ends the solver at once and keeps the frames already saved; a third (or `force`) ends everything in the case's WSL copy. After the solver has ended, while frames are copied back, a Stop lets the copy finish for up to 120 s, then ends everything. A solver whose `system/controlDict` was written less than about 5 s before it started (OpenFOAM's `fileModificationSkew`) may not see the write request; the 20 s rule then ends it, keeping the frames already saved. A case stops too, once, with "Stopped: <Name> was turned off" when its plugin is turned off, with "Stopped: <Name>'s environment was removed", and with "Stopped: plugins were reloaded" when the Reload button in Settings → Plugins reloads plugins; its queued cases leave the queue with a notice. Turning another plugin on or off, and installing an environment, stop nothing. Closing the app (`stop.bat`) or restarting it leaves a running case running in WSL; the app finds it again when it starts, and its stage, time and saved frames go on updating (its residual plot gets no new points). A case WSL does not answer for 10 minutes after a restart ends `lost`; one whose processes in WSL will not stop ends `stopped` with "Its processes in WSL would not stop. Restart WSL (wsl --shutdown) before running more cases".

What the host writes in the case: `w27-case.json` (`rho`, `kinematic_fields`, `frame_fields`, `app`, `plugin`, `study_id`), `system/decomposeParDict` when the run has more than one rank, and the hidden `.magnusim-ran`, `.magnusim-stop` and `.magnusim-run.json`. What comes back: `constant/polyMesh` and `0/` after the steps, the saved frames, `postProcessing` and the logs. Codes: `bad_request`, `invalid_path`, `not_a_case`, `has_results`, `app_not_allowed`, `pre_not_allowed` (400); `plugin_off`, `project_not_found`, `study_not_found`, `not_found`, `no_results` (404); `read_only`, `too_many`, `running`, `busy` (409); `quota` (413); `unavailable` (503, the app could not check the case right now); and as an ended case's `code`, `launch`, `relay_failed`, `lost` and `stuck`. At most 20 cases of a plugin wait in one project's queue (`too_many`). Run output (frames, logs, `postProcessing`, VTK, the mesh, `0/`) counts toward `max_total_mb` and the 100 000-entry cap like any file in the plugin's folder, and so do `solve.sh`'s `.frame-<t>.part` and `.sync_pp` when a copy is cut (they show in listings; delete them). A run is never cut short at the budget; a submit at or over it is refused with `quota`, and writes answer `quota` until files are deleted. Deleting a study drops its queued cases at once; a study whose case runs cannot be deleted ("A case of this study is running. Stop it before deleting the study."). A rename relabels its queued cases.

**One compute slot.** A mesh, a solve and a plugin case never start while another job holds the slot, in any project: Start and Generate read "Add to queue", and the queue runs one job at a time, first in first out across kinds and projects. A project or folder with a running or stopping job cannot be deleted (Home says which), and deleting a project drops its queued jobs. A stopped solve or plugin case holds the slot until its processes in WSL are gone; the Queue title then ends "(stopping)", or "(finishing)" for one whose relay ended, and the Run panel offers Stop for it. A mesh frees the slot when its generator ends, and its WSL processes can run a little longer. After a restart the app checks for solves and plugin cases left running before it starts anything (meshes are not checked): one still running keeps the slot until it ends, and one WSL does not answer for keeps it until WSL answers, 10 minutes at most. A queued job that fails to start three times leaves the queue with a notice.

**Results in 3D (`ws.results.openIn3D(caseRel)`).** Shows a finished case's saved frames in the project's viewer and resolves `{opened}`. It answers `running` while a case of that folder is queued or running, and `no_results` while no complete frame is saved. When other results are on screen the app asks "Open these results?" first, and when the page has unsaved work it asks the leave question; Cancel or Stay resolves `{opened: false}`. Otherwise the workspace closes (so the promise may never settle) and the frames open: no core study is active while they show, picking a study or another geometry closes them, Views and Compare are hidden, the case is drawn at its own size (the project's CAD, which it is not, is hidden), and the units come from the case's `w27-case.json` (the kinematic fields times `rho`, pressure in Pa). With no study active, the colouring lists the default analysis's result fields.

**Solve hooks.** `solve.prepare`, `solve.parse_line` and `solve.stop` fire for core solves and plugin cases; register them in `register(hub)` with `cfddesk.registry.hooks.get_hooks().on(name, fn, plugin=<key>)`. Each listener is called with keyword arguments: `solve.prepare(ctx)` once the hooks have loaded; `solve.parse_line(ctx, lines, events, dropped)` with batches of up to 256 solver output lines or 200 ms, the events parsed from them, and how many lines were dropped because 4096 were waiting; `solve.stop(ctx, forced)` after a stop action. `ctx` is a `cfddesk.registry.solve_context.SolveContext` (`owner` `core` or `plugin`, `project_id`, `simulation_id`, `plugin`, `study_id`, `run_id`, `app`, `case_dir`, `wsl_case`, `n_procs`). Listeners run in the relay process of the solve, which loads every plugin's `register(hub)`, and only when some plugin listens. A core solve never waits for `solve.prepare`; a plugin case waits for loading and `solve.prepare` 5 s at most. The solver's output never waits for a listener: a listener whose call takes over 1 s three times, or that raises once, is dropped for that run with a log line, and `solve.stop` gets 5 s. What a listener prints becomes a `[hook]` log line of at most 500 characters and never reaches the run's events. A listener cannot use its plugin's own environment's packages, and a plugin whose import ends the process, crashes natively or patches the runtime can still end or bend a run. Only `FIRED_HOOKS` (these three, plus `case.write`, `case.written` and `ui.tree.transform`) ever fire; registering one of `RESERVED_HOOKS` is allowed and logs once "hook <name> is reserved and never fires in API 1.3".

**`SolverApp.script_template`** is only a solve job (the builtin `solve`, `solve.sh`). Any other value is ignored with a note in Settings → Plugins ("Solver <label>: script_template "<value>" is not a solve job, so it is ignored. Solves use solve.sh."), and the plugin still loads.

**Attach.** `/api/case/attach` reads only `case_dir` (`case` and `path` answer 400 "use case_dir"). A plugin case's folder needs `plugin` and `plugin_study_id` (together, or 400), and attaches only inside that study's folder (else 403 "case_dir is not in this plugin study"); a core study's folder is checked from the project's `geometries/` or `simulations/` folder, so a plugin case under a folder named `simulations` attaches.

**Busy case files.** While a case of the study runs (until it has ended, stopping included), a `ws.files` write, a commit or a `ws.data` write inside its folder, and a delete inside, of or above it, answer `busy` ("Stop the case, or wait for it to finish, before changing its files"), by the folder's name on disk in any spelling. A write that was already waiting when the case started can still land, and the plugin's own Python (its service, jobs and `scope["data"]`) is not checked. Queued cases may be changed; they are checked again when they start.

## 1.2

Host API 1.2 (`API_VERSION`, and `hostVersion` in a workspace's context), `magnusim_sdk` 1.2.0, workspace SDK 1.1.0. The host does not refuse a plugin whose minor version is newer than its own, so a workspace checks `ws.context.hostVersion` (compare the numbers, `1.2` or later) before it uses anything below; a 1.1 host answers the new calls with code `not_allowed`.

**Optional bundled plugins that ship off.** A bundled plugin that is not required may set `default_enabled = false`: it ships in `bundled-plugins/` but is not imported, its UI and workspace files are not served, it adds no study kinds (so existing projects look unchanged) and Setup does not build its environment, until someone on this PC turns it on in Settings → Plugins. `required = true` with `default_enabled = false` is a load error; user and entry-point plugins ignore the key. The worker remembers the choice in the local JSON, `plugins.enabled` next to `plugins.disabled` (an explicit off wins when both name a key; Node never writes either list). `plugins.list` rows add `default_enabled`, and now list bundled plugins that are off, so they can be turned on. A plugin that requires one that is off fails with "needs the <Name> plugin, which is off". The shipped registry golden (`gen:registry`) holds what a fresh install turns on, so a plugin that ships off never changes it; a test loads every bundled plugin, optional ones included, with nothing failing. `tools/plugin_env.py create-bundled` (`Setup.bat -Plugins`) builds only plugins that are on (`--include-off` for all). Only a plugin that is on gets its `/plugins/<key>/ui/` files served.

**A plugin's files in a project (`ws.files`).** Large and binary files in the plugin's own folder of a project (`projects/<pid>/plugins/<key>/`, the same folder as `ws.data`, `PluginData` and the plugin's studies). The bytes are streamed by the app server and never pass through the Python worker.

| Call | What it does |
|---|---|
| `files.read(rel, {offset, length, ifMatch})`, `files.readBlob(…)` | The bytes, or a range of them, as an `ArrayBuffer` or a `Blob`; `null` when there is no such file |
| `files.stat(rel)` | `{rel, size, mtime, etag}`, or `null` |
| `files.write(rel, data, {ifMatch, sha256, onProgress, signal})` | `data` is an `ArrayBuffer`, a typed array, a `Blob` or a string (written as UTF-8). Sent in 16 MB chunks with progress; the file is replaced in one step only once every byte has arrived, so a reader never sees half of it. `ifMatch: <etag>` replaces only that version, `ifMatch: null` only creates a file that is not there yet (otherwise `changed`). Resolves `{rel, size, mtime, etag, sha256}`. Aborting `signal` leaves the file as it was |
| `files.list(prefix)` | Every file under a folder (`""` is the plugin's folder), at any depth, sorted by `rel`; more than 10 000 rejects with `too_many` |
| `files.delete(rel, {recursive})` | A file, or a folder with `recursive`; resolves `{deleted}` (files removed) |

The etag changes whenever the file does, and `PluginData.file_info` in the plugin's Python gives the same one. Every `ifMatch` is compared as written (`*` is not a wildcard).

Limits: the manifest's `[files]` table, `max_file_mb` (1–4096, default 64) and `max_total_mb` (1–65536, default 512, at least `max_file_mb`), caps what the workspace writes, through `ws.files` and `ws.data`, in the plugin's folder of one project. `plugins.list` rows add `files` (`max_file_bytes`, `max_total_bytes`). The host also keeps 256 MB of the disk free, allows 4 open uploads per plugin, ends an upload idle for 10 minutes, and holds a plugin's folder to 100 000 files and folders. The plugin's own Python (its jobs and service) is not capped.

Refusals reject with an `Error` whose `code` is one of: `invalid_path`, `is_folder`, `not_folder`, `not_found`, `study_record`, `study_not_found`, `project_not_found`, `plugin_off`, `too_large`, `quota`, `disk_full`, `too_many_uploads`, `too_many`, `changed`, `checksum`, `busy` (another program holds the file; a write retries its commit, then gives up), `bad_range`, `unavailable`, and `bad_request`, `offset`, `incomplete` or `upload_not_found` when the upload protocol itself went wrong (the SDK drives it, so a page should not see them). The routes are `/api/plugin-files/stat|list|read|delete` and `/api/plugin-files/uploads` (begin), `uploads/<id>` (a chunk), `uploads/<id>/commit`, `uploads/<id>/abort`. A plugin's uploads end when it is turned off, turned on, reloaded, or its environment is rebuilt or removed. A refused file request shows as a failed request in the app's console (the browser logs every answer that is not 2xx, such as "Failed to load resource: … 409 (Conflict)"); the page gets the refusal as that `Error` with its `code`, so a plugin's own console checks should allow it.

**One set of path rules** for `ws.files`, `ws.data` and `PluginData` (`magnusim_sdk.data.data_rel`; the app server has a copy, and both are tested against `python/tests/fixtures/plugin-file-paths.json`). Backslashes become `/`, whitespace at the ends is trimmed, and empty and `.` parts drop out. Refused (`invalid_path`): a path starting with `/`, `..`, a name with `: ~ < > " | ? *` or a control character, a name ending with a dot or a space, a Windows device name (`con`, `nul.txt`, `com1`, `com¹`, …), a name starting with `.magnusim` (the host's temp and staging files, which listings leave out), a name over 255 characters, more than 32 parts, a path over 240 characters. Nothing writes a study's record (`studies/<sid>/study.json`, any spelling), or a file straight in `studies/` or `studies/<x>` (`study_record`); a file inside a study needs the study (`study_not_found`). A path that runs through a link or junction is checked where it lands. **Changed from 1.1:** `ws.data` now follows these rules (1.1 refused only `..`, `:`, `~` and the study record), counts toward `max_total_mb`, and answers `plugin_off` while the plugin is not on.

**`magnusim_sdk` 1.2.0.** `PluginData` adds `file_path`, `file_info`, `read_bytes`, `open_bytes`, `write_bytes`, `atomic_path` (a temp path next to the file for a writer such as a mesher; it keeps the file's extension and replaces the file when the block ends), `list_files`, `delete_file`, `usage` and `check_room`, with `FileInfo`, `data_rel`, `is_study_record`, `MAX_ENTRIES`, and a `code` on `PluginDataError` (the same codes as above). `PluginData.from_scope(scope)` in a service method, and `PluginData.from_env()` in a plugin job, which is told `MAGNUSIM_PLUGIN_KEY` and `MAGNUSIM_JOB_ID`, and when known `MAGNUSIM_PROJECT_ID`, `MAGNUSIM_PROJECT_DIR`, `MAGNUSIM_SIMULATION_ID` and `MAGNUSIM_GEOMETRY_ID`.

**Plugin lane.** `plugin_studies.*` and `plugin_data.*` run on the plugin worker lane with `plugin.dispatch`, so a busy workspace saving its study never delays the project tree.

**The default analysis comes from the required plugin.** A required bundled plugin may set `default_analysis = { steady = "<key>", transient = "<key>", aliases = ["<name>"] }` (an inline table; `transient` and `aliases` are optional): the analysis a study gets when none is named (a new study, and a study saved before analysis keys), and the names such old studies carry for it (Incompressible Flow: `incompressible`). Both keys must be the plugin's own analyses of that time dependency, or the plugin fails to load; any other plugin that sets it fails to load with "[default_analysis] is only for a required bundled plugin". `registry.describe` (and the shipped registry golden) add `default_analysis` (`null` while the plugin is not loaded); `cfddesk.registry.default_analysis_key()` and `is_default_alias()` read it, and `DEFAULT_STEADY_KEY`, `DEFAULT_TRANSIENT_KEY` and `LEGACY_ANALYSIS_ALIAS` stay importable from `cfddesk.registry` and are read from it when used. The core names no simulation type. **Siblings:** the analysis of the other time dependency is the registered `<x>_steady` / `<x>_transient` pair, else the analysis of the same `family` when the family has exactly one of each (a `dataclasses.replace` clone keeps the family of what it copied, so it gets no sibling of its own). The Create Simulation time dependency offers only what the picked analysis's family has.

**Steady runs go through the run model too.** Every save of a steady run's iterations and write interval (run update, Start, the study control) is stored as `run_model.normalize` returns it, like transient settings: the core rounds and clamps nothing itself. A new run and a study without saved run settings start from the study's steady analysis's `run_defaults` (none when it has no steady analysis); a new study's control file no longer carries numbers of its own.

**A run whose analysis is not installed** (its plugin is off or did not load): `analysis.validate_ready` answers `ready: false` with one issue, "<Plugin> failed to load, so this run can't start." when a required plugin is missing, else "This run's analysis is not available: its plugin is off or did not load.", with the fix `{"go": "plugins"}` (the Run panel's "Open Settings → Plugins"); `analysis.run_monitors` answers no monitors and `unavailable` with that text, instead of an error. The study panel says the same instead of showing another analysis's settings. `required_missing` also lists a required plugin that loaded but was unloaded by cross-reference validation (another plugin dropped a solver, BC type, material or monitor its analyses use).

**Unsaved work (workspace SDK 1.1.0).** `nav.setDirty(dirty, message?)` marks the page as holding unsaved work; a `files.write` on its way counts too. While it is dirty, every way out of the workspace asks first ("Leave without saving?", with the plugin's name and its message: plain text, 200 characters at most, control and bidirectional characters removed): the header's Back to project, `nav.back()`, the browser's Back and Forward, a typed or pasted link, Home and the folder chip, opening another project, and turning the plugin off in Settings → Plugins ("Turn off <Name>?"). Word the message as a sentence: "Leave without saving?" adds a full stop when it does not end with ".", "!", "?" or "…" (a closing quote or bracket after the mark is fine), and "Turn off <Name>?" shows it in parentheses without its one last ".", "!" or "?" (a run such as "..." stays). On these two questions the Stay (or Cancel) button has the focus, and Enter, like Escape, keeps the work: Leave and Turn off take a click. A page's own `ui.confirm` is unchanged (its confirm button has the focus, and Enter answers it). Closing or reloading the browser tab shows the browser's own prompt. The compute queue never leaves a workspace. A study deleted, or the plugin turned off, somewhere else closes the page without asking, and the card adds "Changes that were not saved in the workspace were lost." `nav.back()` now resolves `false` when the user stays. The flag belongs to the page load: reloading the page, or an approved leave, clears it.

**Focus and full screen.** The page gets the keyboard when it connects and again after the app's own dialogs and Settings close, but never while one of them is open. The frame has `allow="clipboard-write; fullscreen"`: `element.requestFullscreen()` from a click or key press puts the page over the whole screen, Esc always leaves, and the app leaves full screen before it shows a dialog (a toast is not seen over a full-screen page). The app's dialogs open one at a time: a page's `ui.confirm` or `ui.prompt` waits its turn, and one from a page that has gone is dropped.

## 1.1

**Analysis contract** (`cfddesk.registry.contract`). Optional fields on `AnalysisType`; the core falls back to a neutral default for any left out, and a plugin that clones a builtin with `dataclasses.replace` keeps the builtin's:

| Field | What the core does with it |
|---|---|
| `family` (`AnalysisFamily`) | Create Simulation title, description, tags; the study's name |
| `study_defaults(time_dependency)` | A new study's settings (published in `registry.describe` as `study_defaults`) |
| `algorithm_label`, `x_axis` | The study panel's Algorithm row; the run's progress axis (`seconds` / `iterations`): the residual and monitor plots, the results timeline, and progress and time left in the Run panel, the job chip and the Home card |
| `residual_series` | The residual plot: per series `key`, `label`, `color`, `fields` (solver-log fields a point takes the largest of), `always` (in the legend before it has values), `dashed` (a per-step metric such as the Courant number, with `max_key`), `swatch` (a legend class). Defaults to one series per `residual_keys` entry |
| `ui` | `study_settings` / `run_settings`: the names of the components the plugin's UI registers for the study and run panels' settings slots (below) |
| `run_monitors(case_dir)` | A run's monitor results for the Graphs panel: `{rho, monitors, custom, balance}` |
| `plan_case(ctx)` | What `write_case` would report, without writing (`prepare_run --validate-only`) |
| `validate_ready(ctx)` | What blocks a run: `[{"message", "fix"}]`. The Run panel's Start button stays off with the first issue as its reason (`GET /api/run/ready`), and it is checked again before the run is marked running |
| `run_model` (`RunModel`) | Run settings: `defaults()` (a new run's, `run_defaults`), `normalize()` (every save of a run's settings, steady and transient, is stored as it returns them, `analysis.run_normalize`; the core keeps no limits of its own; a value it rejects falls back to its default), `preview()` (the Run panel preview) |
| `result_fields` (`ResultField`) | What results colour by, in order: `key`, `label`, `unit_quantity`, `kind` (`scalar` / `vector`). A scalar is shown by its name, a vector `X` by its magnitude `magX` (label "<label> Magnitude"). The Coloring picker lists those the run wrote (a laminar run has no `k`); results open on the first. Names are plain identifiers (a letter, then letters, digits or `_`, 64 at most) |
| `launch` (returns `LaunchSpec`) | Program, `keep_frames` (`all` / `latest`), `process_names`, `stop_strategy`, `frame_fields`, `log_parser` |
| `log_parser` (`LogParserRef`) | The one solver-output parser; Node only aggregates its events |
| `frame_fields` | Fields that mark a written result frame (default: `fields`) |

Worker RPCs: `analysis.describe`, `analysis.defaults`, `analysis.validate_ready`, `analysis.run_normalize`, `analysis.run_preview`, `analysis.launch_spec`, `analysis.run_monitors`. `run.transient_preview` is gone; `analysis.run_preview` replaces it.

**Case sidecar.** `write_case` writes `w27-case.json` in the case folder. Besides `rho`, it lists in `kinematic_fields` the fields the case stores divided by density (pressure in an incompressible case); every results view shows those times `rho`: surface, series range, cut plane, iso surface and plot over path. A case without the list is read as `["p"]` (cases written before 1.1). After `write_case`, the core adds `analysis_key` and `frame_fields` (the launch spec's): results list a saved time only when every frame field is written in it (`U` and `p` for cases without the list).

`prepare_run` reports `app` as the program to run (the solver's `application`, not its registry key), plus `launch` and the boundary-to-patch mapping `bcs`. It refuses a run that is not ready (`{"ok": false, "not_ready": true, "error", "fix"}`) and writes nothing.

**Bundled tier.** `bundled-plugins/` ships with the app and loads after the core builtins and before entry points and user plugins, in dependency order. New manifest fields: `tier = "bundled"`, `required`, `requires_plugins` (also for user plugins), `protected`. A required plugin that does not load blocks creating and running simulations with a message (`registry.describe` → `required_missing`); it cannot be turned off. Incompressible Flow (analyses `incompressible_steady` and `incompressible_transient`, solvers `simpleFoam` and `pimpleFoam`, the `newtonian_incompressible` material model and the `area_average` and `flow_rate` monitors) is the required bundled plugin; the keys are unchanged, so projects need no migration. `MAGNUSIM_BUNDLED_DIR` moves the bundled folder (tests); `MAGNUSIM_PLUGINS_DIR` still moves only the user plugins.

**`magnusim_sdk`** (`python/sdk`, standard library only): `events`, `units`, `foam`, `gmsh_helpers`, `msh22` (numpy imported when used), `proc`, `study` (boundary-condition record helpers), `fluids` (the fluid property library) and `progress` (the solver-log parser engine an analysis's `log_parser` builds on). Plugins may import `magnusim_sdk` and `cfddesk.registry` only (`tools/plugin_boundary.py`).

**Settings slots (in-page UI).** The study panel and the run panel are core chrome (title and rename, Done/Delete, the Start gate, progress, residuals, monitors). The analysis's settings sit inside, drawn by its plugin: `host.pluginUi.registerStudySettings(name, Component)` and `registerRunSettings(name, Component)`, named by the contract's `ui.study_settings` / `ui.run_settings`. A study-settings component gets `{study, row, rows, save, setTimeDependency}`, a run-settings component `{run, row, saveSteady, saveTransient}` (types: `src/plugin-api/slots.ts`). An analysis that names none gets a generic form from its `settings_schema`, `numerics_schema` and `control_schema`. Disabling the plugin removes its components.

**TypeScript UI.** A manifest's `ui_entry` may be `.tsx`/`.ts`/`.jsx`: the host bundles it when it serves it, into one ES module on the host's React (`react` and the JSX runtime resolve to the page's single copy). A plugin UI may import only `react` and files inside its `ui` folder; type-only imports of the host API types are erased. Bundled plugins' UI is served from `bundled-plugins/<folder>/<ui>`.

**Plugin data and studies.** Each plugin has a folder in each project, `projects/<pid>/plugins/<key>/`, created on first write. A plugin method gets it as `scope["data"]` (`cfddesk.registry.plugin_data.PluginData`: `read_json`, `write_json`, `delete`, and the study helpers), bound to the calling plugin and project; a path outside it is refused. These writes are the one exception to "only the worker writes project files".

A manifest's `[[study_kinds]]` (`key`, `title`, `icon` as one SVG path, `workspace`, `schema_version`) declares project-level studies the plugin owns, stored at `plugins/<key>/studies/<sid>/study.json` (`id, kind, title, schema_version, rev, plugin, plugin_name, plugin_version, created_at, updated_at`). The tree shows them in a STUDIES section in every stage, with New / Rename / Delete. RPCs `plugin_studies.list|create|rename|delete` (routes `/api/plugin-studies`); a rename with an old `rev` is refused with HTTP 409 ("This study changed in another tab. Reload to continue."). A study saved by a newer plugin version is read-only. A study whose plugin is off or missing stays on disk untouched, greyed in the tree ("Requires the <Name> plugin", with a link to Settings → Plugins); it can be deleted but not opened or renamed. Scope key: `p:<pid>/plugin:<key>/study:<sid>` (`plugin_study_scope` / `pluginStudyScope`).

**Own environment and service.** A manifest's `[python]` (`requirements` lock, pinned and hashed; `python` range; `service` module; `find_links` wheels folder) gives the plugin its own environment at `.cache/plugin-envs/<key>-<lock hash>/` (`MAGNUSIM_PLUGIN_ENVS_DIR` moves it), built from the core interpreter with `magnusim_sdk` and without `cfddesk`. Until it is built, `plugins.list` rows say `status = "needs setup"` with `python_env = {state: needs_setup | failed | ready, error, tail, lock_hash, service, python_version}`; Settings → Plugins offers Install dependencies (`POST /api/plugins/<key>/env/install`, polled at `GET /api/plugins/<key>/env`; `POST .../env/remove` deletes it; both local-operator only). `tools/plugin_env.py create|check|remove <key>` and `create-bundled` (`Setup.ps1 -Plugins`) do the same from a shell. With a `service`, `/api/plugin/<key>/<method>` answers from `python -I -m magnusim_sdk.service <module>` in the plugin folder: one process per plugin, 30 s per call unless the method sets `timeout_s` (600 max), killed with its children on a timeout, restarted after a crash, stopped after 10 minutes idle and when the plugin is turned off or reloaded. A plugin without a service keeps its in-process `hub.register_method` methods on the plugin lane. Worker RPCs: `plugins.env`, `plugins.env_remove`.

**Jobs and filters on the plugin's environment.** `JobKind.python = "plugin"` runs a job's tool on the plugin's environment in its folder (`jobs.describe` rows add `runtime`, `python`, `cwd`, and `python_error` while it needs setup: starting it answers 409). A plugin with an environment runs its filter tools there too. Stopping a job ends its whole process tree.

**Study migrations.** Plugin study rows add `schema_version`, `kind_schema_version` and `needs_migration`; the host upgrades older ones in the background through the service's `migrate_study` and `plugin_studies.get` / `plugin_studies.migrated` (rev-checked; the tree says `plugin_studies_migrating` meanwhile). A study of a plugin that needs setup is greyed with "<Name> needs setup".

**Requirements checked for real.** `wsl_tool` requirements are checked against a cached probe of the WSL toolchain (unknown until it answers, never reported missing then); `python` ones against the plugin environment's installed packages; `gpu` is reported as a note (`notes`) and never blocks.

**`magnusim_sdk` 1.1** adds `data` (`PluginData`, the one copy; `cfddesk.registry.plugin_data` re-exports it) and `service`.

**Workspaces.** A manifest's `[[workspaces]]` (`key`, `title`, `icon` as one SVG path, `entry`: an `.html` file in the plugin's `workspace/` folder, `workspace/index.html` by default) declares a full page the plugin draws. A study kind's `workspace` names one; it must be declared, or the plugin fails to load with that message. A study of that kind opens in it at `#/p/<pid>/ws/<plugin>/<workspace>/<sid>`, over the project's workbench: the tree and the active study stay as they were, and Back, reload, browser history and deep links work. The host draws the header: Back to project, `<Plugin> › <Study>` (click to rename), Queue and Settings. The header's Workspaces menu (shown only while an enabled plugin has a workspace) names a new study and opens it. `plugins.list` rows add `workspaces`; study kinds and study rows add `workspace` (`""` when there is none).

The page runs in a sandboxed frame (`sandbox="allow-scripts allow-downloads"`, an opaque origin), served from `/plugins/<key>/workspace/` while the plugin is on. Its Content-Security-Policy allows scripts, styles and fonts from `/plugin-sdk/` and its own folder, `fetch` to its own folder only, images and media from its own folder plus `data:` and `blob:`, workers from `blob:`, WebAssembly, and no inline script but the host's import map. It cannot reach the app's page, the app's API, `localStorage`, IndexedDB or cookies.

**Workspace SDK 1.0** (`/plugin-sdk/`). The host puts an import map and `/plugin-sdk/theme.css` (the `--mg-*` design tokens and base styles) first in every workspace page. The import map names `react`, `react-dom/client`, `react/jsx-runtime` and `react/jsx-dev-runtime` (the app's React as ES modules, one copy), and `@magnusim/workspace` (the bridge). `docs/plugins/plugin-sdk.json` gives the versions and the import map; `docs/plugins/workspace-sdk.d.ts` (also served as `/plugin-sdk/workspace.d.ts`) gives the bridge's types. `npm run gen:plugin-sdk` regenerates both, and CI checks they are current. `connect()` says hello and gets the context (plugin, workspace, project, study, units, theme) and a private port; every call then goes over that port, scoped to the plugin, the project and the study:

| Call | What it does |
|---|---|
| `service(method, params)` | Its own backend (`/api/plugin/<key>/<method>`), never another plugin's |
| `jobs.start(kind, params)`, `jobs.events(id, fn)`, `jobs.stop(id)` | Its own job kinds (a start that names another plugin's kind is refused, 403); events and Stop only for jobs this workspace started |
| `study.get()`, `study.update(patch, rev)` | Its study; a stale `rev` is refused. The host keeps `id`, `kind`, `plugin`, `plugin_name`, `plugin_version`, `schema_version`, `created_at`, `updated_at` and `rev` |
| `data.read(rel)`, `data.write(rel, doc)` | JSON in its own folder of the project (8 MB at most, the one request allowed past the app's 2 MB JSON limit). `..`, `:` and `~` are refused, and so is a study's record (`studies/<sid>/study.json`, any spelling) |
| `project.info()`, `call('prefs.units')`, `call('theme')` | Read-only project title and units, the theme |
| `ui.toast`, `ui.confirm`, `ui.prompt`, `nav.back` | The app's toast and dialogs; close the workspace |
| `on('units' \| 'theme' \| 'study', fn)` | Changes the host pushes while it is open. `study` carries the record after a rename in the header or a save, so the next `study.update` uses its `rev` (`context.study` follows too) |
| `spawnWorker(url)` | A worker running your module (the sandbox refuses `new Worker(url)`); messages posted before your module has loaded are held and delivered to it in order |

Anything else answers `not allowed: …`, and the host logs it. A page that has not connected 5 s after it started loading gets an error card (Open Settings → Plugins, Try again). A study deleted while it is open, or a link to one, shows "This study no longer exists." with Back to project. Worker RPCs `plugin_studies.get|update` and `plugin_data.read|write` (routes `/api/plugin-studies/get|update`, `/api/plugin-data/read|write`); a missing study answers 404 `study not found` (`magnusim_sdk.data.StudyNotFoundError`).
